综合项目：把信息论连接成一个真实可复现的系统

从符号分布、最短前缀码、精确算术区间到纠错与二元对称信道；把每一个编码器、译码器、长度字段和失败模式都变成可以断言的程序。

从公式走到端到端系统

信息论的三个层次分别回答：一个数据源有多少平均不确定性？怎样用较短的符号串表达它？噪声破坏这些符号后，接收端怎样恢复？如果只写一个“压缩比”或“误码率”，就很难看出哪一层出了问题。构建可复现实验，要把三层拆开测试，再以真实的数据帧将它们连接起来。

下面三个项目都能直接运行 Python 标准库代码，无需 NumPy 或网络。它们刻意保留一些工程边界：Huffman 动态码本需要传输或预共享；教学版精确分数算术编码不等于标准流式协议；LZW 的整数码列表没有序列化为真实比特流；Hamming(7,4) 只保证纠正每个七位码字中的一个比特错误。

项目一：概率分布与信息量计算器

离散概率分布 p=(p₁,…,pₖ) 必须满足每项非负、总和为 1。熵使用 bit 单位：

H(p)=−∑iKpilog2pi
(28.1)

两组概率 p、q 的 KL 散度同样使用以 2 为底的对数。当 pᵢ>0 但 qᵢ=0，KL 是正无穷，绝不能为了避免除零就偷偷加一个常数并宣称仍是精确 KL。互信息则可由完整的联合频数表计算，独立时总体互信息为零；有限样本经验互信息不一定为零。

DKL(p‖q)=∑iKpilog2piqi
(28.2)
from examples.capstone import entropy, kl_divergence
from examples.information_learning import empirical_mutual_information

assert entropy([0.5, 0.5, 0]) == 1.0
assert kl_divergence([1, 0], [0, 1]) == float("inf")
assert empirical_mutual_information([0,0,1,1], [0,1,0,1]) == 0.0

验证时不只检查典型值，还必须覆盖全零概率项、总概率不是 1、联合表不一致与 KL 支持集不重合。代码中的 entropy 和 kl_divergence 是概率已知情况下的精确计算，不会凭空推断真实分布。

项目二：Huffman、算术与 LZW 的往返验证

选择短消息 AAAABBCD。出现次数为 A:4、B:2、C:1、D:1。最优二元 Huffman 前缀码的一种构造是 A→0、B→10、C→110、D→111；平均码长为 4/8×1 + 2/8×2 + 2/8×3 = 1.75 bit/符号，八字符正文一共 14 bit。

由于四个字符可以先约定两位固定长度编码，裸符号串是 16 bit；Huffman 正文虽然只有 14 bit，但完整文件还需要码本、原始长度和必要的帧信息。对这么短的消息，元数据可能让“压缩文件”反而更大。这里的 14/16 不是可直接与 gzip 比较的完整压缩率。

精确算术编码在有理数区间 [lo,hi) 内迭代缩小区间；每步先保存旧的 lo、hi，再同时使用同一个旧区间宽度更新两个边界。教学实现利用 Python Fraction 避免有限精度舍入，并在最终区间内挑选完整包含于其中的二进制 dyadic 子区间。它可无损往返，但没有实现流式 renormalization、EOF/帧协议或标准文件格式。

LZW 实现输出整数索引序列并能从同一初始 256 字节字典还原输入，但整数索引本身不等于序列化后的压缩字节。一个公平的压缩对比还必须指定码宽增长、字典重置、文件头与整个包的比特长度。

from examples.capstone import (
    huffman_encode, huffman_decode,
    arithmetic_encode, arithmetic_decode,
    lzw_encode, lzw_decode
)
text = "AAAABBCD"
hbits, book = huffman_encode(text)
assert huffman_decode(hbits, book) == text
abits, model, n = arithmetic_encode(text)
assert arithmetic_decode(abits, model, n) == text
codes = lzw_encode(text.encode("utf-8"))
assert lzw_decode(codes) == text.encode("utf-8")
print("Huffman 正文比特:", len(hbits))  # 14
print("算术正文比特:", len(abits), "需要模型及长度元数据")
print("LZW 输出整数索引数:", len(codes), "非序列化比特数")
编码方法此处验证目标未包括的实际成本
Huffman前缀性质、往返、平均码长码本、原始长度、帧头
算术区间更新、dyadic 子区间、精确往返频率模型、长度、流式有限精度
LZW字典增长、特殊 KwKwK 分支、整数码往返码宽、字节打包、字典重置与封装

每一比特都要有位置：码本、填充与帧协议

压缩正文 14 bit 要交给 Hamming(7,4) 信道码，每四个数据位形成七个传输位。为了分块，我们补 2 个已知零，变成 16 bit 的输入，共四块，传输 4×7=28 bit。接收方必须知道原始正文长 14 bit，才能在纠错后删除填充位，不把它们误当消息。

注意：信源压缩和信道纠错的目标相反。Huffman 希望去除可预测冗余以节省平均码长；Hamming 刻意增加结构化校验冗余以应对噪声。单个包的物理总长度甚至可能超过压缩前未保护的长度，这不代表压缩算法错误，而是比较的边界不同。

Hamming(7,4)：显式纠错位置与限制

本实验规定位置按从左到右 1–7编号，奇偶校验位在位置 1、2、4；数据位依次放在 3、5、6、7。对输入四位 (d₁,d₂,d₃,d₄)，偶校验位分别为 p₁=d₁⊕d₂⊕d₄、p₂=d₁⊕d₃⊕d₄、p₄=d₂⊕d₃⊕d₄。

c=(p1,p2,d1,p4,d2,d3,d4)
(28.3)

示例 1011→0110011；若第 5 位被翻转，收到 0110111，综合征为二进制 101₂=5，因此恢复第 5 位。两个及以上错误时，综合征不再可靠地标识唯一真实错误位置：标准单错译码器可能误纠正为另一个合法码字，甚至未检测到某些错误。这里没有添加整体 CRC 或外层 ARQ，因此“无报警”绝不等于“无误码”。

项目三：从压缩到有噪信道再到重建

完整链路依次执行：Huffman 前缀编码 → 记录正文 bit 长度并填充 → Hamming(7,4) 编码 → BSC 对每个传输位以概率 p 独立翻转 → syndrome 单错译码 → 去填充 → Huffman 译码。噪声使用固定随机种子以便对照，网页实验和 Python CLI 都是教学模拟，而非真实无线电链路。

p=0.00；正文=14 bit；信道=28 bit；翻转=0；译后残余 bit 错误=0；消息恢复=成功

固定示例 AAAABBCD、码本预共享、固定种子。单次消息结果不能代替误码概率统计；syndrome 不保证检测两个及以上错误。

读这个实验时，应区分三件事：物理传输中的翻转数、纠错后源编码 bit 的残留错误数、以及最终字符序列是否完全一致。对于变长前缀码，单一残留 bit 错误可能改变后续码字边界，因此即使物理 BER 很小，也不代表整包消息一定可靠。

实验默认预先共享 Huffman 码本、源正文 bit 长度及消息的帧边界；这些成本未计算在 28 bit 的物理传输长度中。若要做真实压缩率或系统吞吐量比较，必须设计并统计元数据、纠错、重传、同步与文件封装。

单码字块错误率：可解析的对照

对独立 BSC，若每个传输 bit 以概率 p 被翻转，一个七位 Hamming(7,4) 码字在标准单错译码后准确恢复原四位数据的条件恰好是七位中至多一个错误。因此每个七位码字的译码后块错误率为：

Pblock=1−(1−p)7−7p(1−p)6
(28.4)

这里使用“块错误”而非“单码字 bit 错误率”，是因为一次超过纠错能力的错误可能改变多个信息位。四个 Hamming 码字组成的整包，即使每块独立，整包成功率也必须考虑四块联合事件和源译码规则。不要把公式中的 p 当作 SNR：如果信道是 AWGN，还需先指定调制、解调以及从 SNR 到 bit 翻转概率的映射。

最终可以得出什么结论？

整个课程从“消息为什么有信息量”出发，到本章实现了可测量、可逆向校验的链路。你已经能区分概率熵、编码平均码长、传输占用、码字错误与最终任务失败；能明确指出哪个假设属于信源，哪个属于信道，哪个属于解码器。

下一阶段适合开展真正的工程性能研究：为压缩码流加入自描述帧头和版本号，加入 CRC 检错与 ARQ 重传，使用同一原始数据集测量总线速率，并在相同物理信道使用次数下对比不同纠错码。任何收益结论都应附实验条件、软件版本、误差条与失败案例。
